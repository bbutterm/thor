# Промт: разбивка кода «Тор: Достойная смерть» на модули

Кому: агенту, который может работать в репозитории и запускать Godot — Claude Code (облачная сессия на `bbutterm/thor`) или аналог. Чат-модели без запуска тестов это не годится. Давать **по одному этапу на сессию**: в начале — текст ниже, в конце — номер этапа.

---

Ты работаешь в репозитории игры «Тор: Достойная смерть» (Godot 4.6.3, GDScript со статической типизацией, Jolt). Сначала прочитай `CLAUDE.md` — там правила проекта, команды тестов и правила против фризов. Общение с владельцем и комментарии в коде — на русском.

**Цель.** Разбить код на небольшие модули так, чтобы под конкретную задачу хватало 2–3 файлов, короткой документации своей папки и 2–3 тестов, а не всего проекта.

**Главное правило: поведение игры не меняется.** Это чистый рефакторинг. Никаких новых фич, правок баланса или «заодно починил». Нашёл баг — запиши его в `docs/refactor_notes.md` и не трогай.

**Как работать:**
- Один этап за сессию, внутри — маленькие шаги. После каждого шага: `godot --headless --path . --import`, затем тесты затронутого модуля, затем отдельный коммит.
- В конце этапа — **все** `tests/*_test.tscn`, у каждого 0 FAIL и 0 SCRIPT ERROR. Только после этого push в `main`.
- Логи тестов обрезай: `godot … 2>&1 | head -c 50000000 > log`, код выхода — `${PIPESTATUS[0]}`.
- Переносишь скрипт — проверь все `.tscn`, `.tres` и `preload`, которые на него ссылаются (`grep -rn "<старый путь>"`), и `class_name`. Генерируемые сцены правь через `tools/build_scenes.gd` и перегенерируй. Ручные арены (`MANUAL_SCENES`) не трогай генератором. После генератора откатывай только те `.tscn`, где изменились одни `unique_id`, **по одному файлу**, никогда не всю папку.
- Числа-«ощущения» остаются `@export` и с теми же значениями.
- Не трогай `NEXT_PHASE.md`.
- Если в работе есть параллельные ветки (`wip/*`, ночная очередь в `NEXT_TASKS.md`), не режь файлы, которые они меняют. Сначала их слить.

**Защита от поломок (обязательно):**
1. **Утверждения в тестах не менять.** Разрешено править в тестах только пути, имена классов и полей после переноса. Каждую такую правку перечислить в отчёте. Если тест не проходит без изменения проверки, значит, поменялось поведение: шаг откатить.
2. **Две попытки на шаг.** Если после шага что-то покраснело и за две попытки не чинится, откатить шаг (`git checkout -- <файлы>` или `git reset --hard` до последнего зелёного коммита), записать проблему в `docs/refactor_notes.md` и перейти к следующему шагу.
3. **Один перенос — один коммит.** Полный прогон всех тестов — перед каждой заливкой в `main`. Красное в `main` не заливать.

**Сколько думать (уровень проработки):**
| Этап | Уровень | Почему |
|---|---|---|
| 1. Документация, тесты по изменениям | низкий | перекладывание текста и простые скрипты |
| 2. Игрок | средний | общее состояние между компонентами, порядок `_physics_process` |
| 3. Враги | средний | наследование, сцены в генераторе, `apply_def` |
| 4. Генератор | низкий или средний | годится низкий, если строго проверять дифф: перегенерация = те же `.tscn` |
| 5. Эффекты и прочее | низкий | фасад `FX` с переадресацией вызовов |

### Этап 1. Документация по папкам и тесты по изменениям (самое выгодное, начать с него) — ✅ сделан 28.10, см. `docs/refactor_notes.md`
1. Корневой `CLAUDE.md` сократить до карты проекта и общих правил: фризы, слои физики, генератор и ручные сцены, локализация, команды проверки. Не больше ~2 страниц.
2. Подробности разнести в `CLAUDE.md` внутри папок: `player/`, `weapons/`, `enemies/`, `rooms/`, `run/`, `ui/`, `scripts/`, `tests/`. Каждый файл — что лежит в папке, публичный API (функции и сигналы, которые зовут снаружи), куда смотреть при типовых задачах, какие тесты проверяют папку. Claude Code подгружает такой файл сам, когда работает в этой папке. Ничего из нынешнего `CLAUDE.md` не потерять — только переложить.
3. `tests/test_map.json`: какая папка или файл → какие тесты. Полный прогон уже есть — `tools/run_test_suite.sh` (отдельная папка данных, лимит логов, сводка ошибок); не делать второй такой же, а расширить его или вызвать из `tools/run_tests.py`:
   - `--changed` — тесты по `git diff` от `main`;
   - `--all` — все тесты;
   - `--test <имя>` — один тест.

   Вывод — строки ИТОГ и общий код выхода.
4. Чтобы тесты можно было гонять параллельно, каждому тесту — свой файл сохранения и настроек, а не общие `user://test_save.json` и `user://test_settings.cfg`. Добавить `--jobs N` в `run_tests.py`. Цель — полный прогон быстрее 25 минут.

### Этап 2. Игрок (`player/player.gd`, ~1340 строк)
Разнести на узлы-компоненты под `Player`:
- `PlayerMovement` — бег, разгон, подкат;
- `PlayerJumps` — прыжки, отскоки, уступ, стена;
- `PlayerSlam` — удар-приземление, пике, супер-прыжок;
- `PlayerDash` — рывок и заряды;
- `PlayerHealth` — здоровье, урон, смерть.

`player.gd` остаётся сборкой и общим состоянием, публичный API — прежний: `deal_damage`, `take_damage`, `modify_stat`, сигналы. Внешний код и тесты не должны заметить разницы. Если для совместимости нужны обёртки — оставь их и пометь `## совместимость`.

### Этап 3. Враги (`enemies/enemy.gd`, ~1170 строк)
- `Enemy` — общая база: ИИ движения, урон, смерть, оверлей.
- Подклассы на особые виды, как уже сделано у `BossEnemy`: корм, Раздутый, Щитоносец, Шаман, Наёмник Локи, метатель.
- Сцены врагов в генераторе перевести на свои скрипты.
- `apply_def` и `EnemyDef` оставить как есть.

### Этап 4. Генератор (`tools/build_scenes.gd`, ~1390 строк)
- Данные залов (`room_defs()`) вынести в отдельные файлы: по одному на зал, например `tools/rooms/room_07.gd` с функцией `def()`, или `.tres`.
- Сборку игрока, врагов, пропсов и UI разнести по файлам `tools/build/*.gd`.
- Проверка: перегенерация даёт те же `.tscn`, отличаются только `unique_id`. Убедись в этом диффом.

### Этап 5. Эффекты и прочие крупные файлы
- `scripts/fx.gd` → модули: удары, взрывы, стихии, декали, экран. Общий `FX` остаётся фасадом, чтобы вызовы `FX.xxx` в коде не менялись.
- Дальше по размеру, только где реально помогает: `scripts/comic_fx.gd`, `scripts/dialogue_manager.gd`, `run/run_manager.gd`, `ui/hud.gd`.

**Отчёт в конце каждого этапа** — в `docs/refactor_notes.md`:
- что куда переехало (таблица «было → стало»);
- какие обёртки совместимости остались;
- найденные и не тронутые баги;
- время полного прогона тестов до и после.
