# GLES3: стресс instance-uniform в одном зале

Барьер перехода залов не решает переполнение при большом числе одновременно живых и ранее использованных эффектов. Это проверено в одном `room_06`, без переходов, на `scenes/game.gd` SHA-256 `ee7fc058e14d1963587175537938d468d77477a3fd987ee6ada14ca7e0bafb54`: Godot 4.6.3, GL Compatibility, Mesa llvmpipe, Xorg dummy, 320×180, `--fixed-fps 60`, `LP_NUM_THREADS=4`.

В каждом отдельном процессе прогрев первого зала заканчивался, затем создавались 20 или 44 живых fodder/grunt с работающими ИИ, физикой и анимацией. Тор и враги сделаны практически бессмертными. Пять раз по всем врагам вручную вызывался игровой `Enemy.take_hit(..., "ranged")` порциями по 11 с паузами между сериями; это запускало обычные вспышки и эффекты. Всего 100 попаданий при 20 врагах и 220 при 44. Это искусственная синхронизация попаданий, а не запись обычной игры.

При 44 врагах ошибки начались после первой серии попаданий и повторялись в дальнейшем; смены зала не было. В начале B1/B2 у врагов было 263/262 меша, пригодных для вспышки. Это количество не равно занятым слотам: механика скрытых узлов и распределение буфера движком сложнее. Утечки двух GL-текстур при завершении также присутствуют в контрольных прогонах. Коды выхода всех четырёх процессов — 0, несмотря на ошибки в B.

Результат доказывает наличие проблемы в этом воспроизводимом стресс-сценарии и оставляет её открытой. Он не определяет частоту переполнения в реальном бою, не измеряет целевую видеокарту и не доказывает, какой из нескольких компонентов нагрузки следует изменить. Исходники и сценарий запуска — в [bench](bench/), метаданные и полные журналы — в [results](results/). Для повторения абсолютные пути в сценарии запуска нужно адаптировать к своей копии; не запускать одновременно с другими графическими замерами.
