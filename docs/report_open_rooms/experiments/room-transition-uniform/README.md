# GLES3: переход между залами и instance-uniform

В Godot 4.6.3 старый `Room` при переходе удаляется из дерева и ставится в очередь на освобождение. Без ожидания прогрев следующего зала начинался в том же кадре, пока прежние геометрические RID ещё живы. При достаточном числе ранее использованных эффектов и вспышек это может переполнить общий буфер instance-переменных GLES3.

Барьер ждёт уничтожения старого зала и тех прямых детей Game, которые уже удалялись при переходе, до создания нового зала и `ShaderWarmup`. Первый вход остаётся синхронным; на переходе игрок временно приостанавливается. Пауза сохраняет экран загрузки, повторные запросы до завершения перехода объединяются, а выход, перезапуск и смерть отменяют ожидающую загрузку. `force_sync` не вызывается. Таймер старого зала хранит `WeakRef`, поэтому не запускает новый зал и не обращается к освобождённому объекту.

Снятие материала само по себе не означает освобождение слота: в исходном коде [InstanceUniforms Godot 4.6.3](https://github.com/godotengine/godot/blob/4.6.3-stable/servers/rendering/instance_uniforms.cpp#L41) записи параметров остаются после инвалидирования. Аналогично при смерти врага его прежние меши переносятся в труп в старом зале. Счётчик `FX.instance_uniform_users` видит текущие материалы, но не все такие ранее использованные узлы; он не равен занятости буфера драйвера.

## Изолированный GL A/A/B

База `6a5baec`, Godot 4.6.3, GL Compatibility, Mesa llvmpipe, Xorg dummy, 320×180, `--fixed-fps 60`, `LP_NUM_THREADS=4`. В одном worktree запускались отдельные процессы с исходным `Game` и барьером без синхронизации рендера. Сценарий принудительно переводил `room_06 → room_07` и создавал обычные игровые FX; это не запись реального забега. До начала нового прогрева ошибок переполнения не было. Счётчики ошибок ниже относятся ко времени выполнения **до** `END_TRANSITION_AB`.

| Сценарий | Исходник A1 / A2: переполнение, повторный RID | Барьер B на `_process`: переполнение, повторный RID |
| --- | --- | --- |
| 14 живых врагов, 20 активных FX | 0 / 0; 0 / 0 | 0 / 0 |
| 24 живых врага, 58 ранее использованных FX | 51 / 72; 52 / 73 | 0 / 0 |
| 10 реальных трупов в зачищенном зале, игровые FX | 0 / 0; 0 / 0 | 0 / 0 |

В усиленном сценарии перед выходом эвристика «текущие материалы + скрытые узлы пула» давала 202, 203 и 199 на A1, A2 и окончательном B соответственно. Это не счётчик драйвера. При начале прогрева в A ещё существовали старый зал и поставленный на удаление пул; в B оба уже были уничтожены. A/A и B подтверждают эффект барьера для этой искусственной нагрузки, но не устанавливают причину всех ошибок длинного игрового забега. В варианте с трупами 10 тел находились в старом зале и непосредственно перед выходом, и во время затемнения; отсутствие ошибок в обеих версиях не доказывает необходимость барьера при таких условиях. Оценка 84 для трупов не учитывает их исторические параметры.

Контроли окончательного B проверили один переход при двух запросах, паузу после удаления старого зала, выход в меню до таймера и во время ожидания. В headless тесте `room_transition_test` прошли **26 OK / 0 FAIL**, включая синхронный первый вход, паузу до и после таймера, удаление Game и перезапуск; сообщений очистки не было. `vfx_test` — 64/0 без сообщений очистки, `destructible_test` — 65/0 с 27 удержанными ресурсами при выходе, `trial_test` — 73/0 с 19 удержанными ресурсами при выходе. Повторный импорт чистый; полный набор после изменения не запускался.

Полные журналы: [исходный усиленный A1](results/A_stress1.log.gz), [A2](results/A_stress2.log.gz), [окончательный B](results/B_process_stress.log), [контроль трупов B](results/B_process_corpses.log), [пауза и двойной запрос](results/B_process_controls.log), [отмена до таймера](results/B_process_cancel_pending.log), [отмена во время ожидания](results/B_process_cancel_detached.log) и [headless регрессия](results/room_transition_test.log.gz). Остальные A/A и экспериментальные логи — в [results](results/). Скрипты и точные копии исходной и измеренных версий сохранены в [bench](bench/); их абсолютные пути нужно поправить для другого окружения. SHA-256 окончательного `scenes/game.gd`: `ee7fc058e14d1963587175537938d468d77477a3fd987ee6ada14ca7e0bafb54`.

Во всех 17 графических процессах после маркера конца появились две ошибки очистки GL-текстур по 349 524 байта. В двух ошибочных усиленных A дополнительно появилась ещё одна ошибка повторной регистрации RID после маркера. Godot вернул код 0 даже при ошибках GLES3, поэтому журнал, а не один код выхода, определяет результат.

Первый графический B использовал ожидание через корутину. Контроль очистки обнаружил `PagedAllocator` при удалении Game с приостановленной корутиной; для окончательного B слабые ссылки хранятся как состояние и проверяются в `_process`, без `await` у удаляемого Game. Все перечисленные выше проверки окончательного B проведены именно на его указанном SHA. Возможное исчерпание буфера **внутри одного длинного боя** этот барьер не решает: [отдельный стресс в одном зале](../one-room-uniform/README.md) воспроизводит его при синхронизированных попаданиях по 44 врагам. Необходима проверка полного игрового прохождения; замеры llvmpipe не характеризуют задержку на целевой видеокарте.

## Восстановление стенда

Скрипты являются архивом фактических запусков, а не установщиком: они используют абсолютные пути и некоторые **перезаписывают `scenes/game.gd`**. Повторять только в отдельной копии проекта; для исторической версии можно взять коммит `87fba24` с базой `6a5baec`. Изменения в поздней версии игры или настройках влияют на сопоставимость. Нужны Godot 4.6.3, Xorg с dummy-драйвером, Mesa llvmpipe и свободное окно рендера. Сначала создать отдельный каталог результатов и поправить значения `project`/`out` в копиях выбранных скриптов; архивные файлы остаются неизменными.

Для усиленного A/A и окончательного B скопировать `bench/transition_uniform_stress.gd.txt` в `tests/transition_uniform_ab.gd`, а `bench/transition_uniform_ab.tscn.txt` — в `tests/transition_uniform_ab.tscn`. В каталог результатов скопировать `bench/game-original.gd.txt` и `bench/game-prototype.gd.txt` под именами `game-original.gd` и `game-prototype.gd`. `run_stress.sh.txt` последовательно запускает исходные A и **старый вариант B с корутиной**, после чего оставляет в проекте `game-prototype.gd`; его B нельзя принимать за результат окончательной версии. Для окончательного B скопировать `bench/game-process.gd.txt` в `scenes/game.gd`, проверить указанный выше SHA-256 и выполнить `run_process_b.sh.txt`, который сам проверяет SHA до и после серии. Оба скрипта пишут полные отдельные логи и ограничивают размер файла; проверять сообщения после `END_TRANSITION_AB` тоже.

Для ранних A1/A2/B1 с 14 врагами вместо стресс-сценария использовать `bench/transition_uniform_ab.gd.txt` под тем же именем в `tests/` и `run_ab.sh.txt` с теми же архивными `game-original.gd`/`game-prototype.gd`. Для headless-контроля очистки `bench/cleanup_probe.gd.txt` и `bench/cleanup_probe.tscn.txt` скопировать в `tests/room_transition_cleanup_probe.gd` и `.tscn`; в копии `run_cleanup_controls.sh.txt` также поправить абсолютный путь к `game-original.gd`, а выбранную версию `Game` сохранить в каталоге результатов как `game-current.gd`. Отдельно запускать контроль исходника, корутины и `_process`: подмена версии меняет смысл метки `candidate`.
