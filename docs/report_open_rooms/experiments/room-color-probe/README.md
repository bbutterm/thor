# Диагностический стенд стоимости цвета

Этот стенд не меняет игровые материалы и не входит в экспорт: `tests/*` исключены из `export_presets.cfg`. Эксперимент предназначен для оценки потенциальной стоимости вычисления цвета, а не сохранения качества и не является доказательством ускорения.

В одном процессе сравниваются исходный зал до Б0 (`tests/fixtures/room_01_before_b0.tscn`), исходный Н3, упрощение только `Dress/FloorVisual`, только `Dress/GroundSkirt`, только `Dress/Backdrop/Ground`, двух поверхностей окружения вместе и всех трёх вместе. Камера, геометрия, окружение и 44 неподвижных врага общие; ИИ и боевые действия выключены. Сцена ставится на паузу, каждый вариант отдельно прогревается, затем выполняются два прохода по 60 кадров в прямом и обратном порядке. Измеряется системное время кадра, выводятся среднее, медиана, p95 и draw calls. PNG каждого варианта сохраняется только для проверки того, что нужные поверхности действительно изменились.

`surface_color_probe.gdshader` намеренно заменяет цветовую композицию однотонным цветом, а шероховатость — средним двух исходных значений. Текстуры цвета, оба слоя и шум визуально теряются. Параметры карты нормалей, затенение по цвету вершин, расчёт AO, модель освещения и геометрия остаются; свет может выглядеть иначе из-за изменённого цвета и шероховатости. Это другая шейдерная программа, поэтому разницу нельзя считать строгой верхней границей будущего ускорения: драйвер может оптимизировать её иначе, а полученный вариант визуально непригоден для игры.

## Измерение

Godot 4.6.3, GL Compatibility, Mesa 25.0.7 llvmpipe, 320×180. Других тяжёлых процессов во время прогона не наблюдалось; каждый замер — 60 кадров, 44 неподвижных врага. Порядок вариантов во втором проходе обратный.

| Вариант | Среднее, мс: 1 / 2 | Медиана, мс: 1 / 2 | p95, мс: 1 / 2 | Draw calls |
|---|---:|---:|---:|---:|
| Исходный зал | 132,11 / 127,64 | 129,96 / 125,81 | 157,99 / 142,32 | 2481 |
| Н3 | 137,26 / 155,07 | 135,57 / 154,68 | 172,00 / 183,84 | 1806 |
| Н3, упрощён только пол | 152,48 / 141,26 | 150,26 / 137,19 | 184,09 / 166,62 | 1806 |
| Н3, упрощена только юбка | 157,43 / 136,18 | 154,61 / 133,96 | 197,62 / 152,99 | 1806 |
| Н3, упрощена только дальняя земля | 140,58 / 141,60 | 138,21 / 141,75 | 165,36 / 157,05 | 1806 |
| Н3, упрощены юбка и дальняя земля | 149,46 / 146,81 | 149,16 / 144,55 | 178,84 / 168,86 | 1806 |
| Н3, упрощены все три поверхности | 147,52 / 146,51 | 148,65 / 141,13 | 167,60 / 190,49 | 1806 |

В первом проходе упрощённый пол оказался медленнее исходного Н3, во втором — быстрее; то же верно для совместной замены трёх поверхностей. Разброс большой, поэтому устойчивый выигрыш и его величина **не доказаны**. Даже сильное визуальное упрощение не показало надёжного возврата к скорости исходного зала в этом тесте. Эти числа не измеряют реальный GPU и активный бой.

На [исходном кадре Н3](original.png) при замене [пола](floor-probe.png) изменились 13 768 пикселей из 57 600, только юбки — 493, только дальней земли — 78, [обеих поверхностей окружения](exterior-probe.png) — 518; эти данные описывают только выбранный ракурс. Следовательно, заключение о дальней земле особенно ограничено: бо́льшая часть не попала в кадр или закрыта. Для оценки окружения нужен другой обзор, в том числе вид из башни.

Стенд отработал с кодом 0; headless-проверка также завершилась с 44 врагами и кодом 0, но не измеряла графику. После `COLOR PROBE COMPLETE` GL-движок сообщил о двух неосвобождённых текстурах и объектах `ObjectDB`. Сохранены [полный графический лог](bench.log) и [лог headless-проверки](headless-smoke.log).

Запускать только в выделенное окно без других тяжёлых процессов и после импорта проекта. Нужен X11/виртуальный дисплей; `--headless` не измеряет рендер. Пример для llvmpipe:

```sh
set -o pipefail
XDG_DATA_HOME=/tmp/thor-color-probe LIBGL_ALWAYS_SOFTWARE=1 \
  godot --path . --fixed-fps 60 --rendering-method gl_compatibility \
  --audio-driver Dummy --resolution 320x180 \
  res://tests/room_color_probe.tscn -- /tmp/thor-color-probe-shots \
  2>&1 | head -c 50000000 > /tmp/thor-color-probe.log
```

При необходимости второй аргумент после каталога кадров задаёт количество измеряемых кадров в проходе; минимум 10, по умолчанию 60. В каждом повторе нужно проверить полноту журнала, отсутствие ошибок компиляции шейдера, правильность количества врагов и кадров, а также сравнить с исходной сценой. Для выводов о пользовательской производительности необходимы целевая видеокарта, другой рендерер, больше ракурсов и активный бой.
